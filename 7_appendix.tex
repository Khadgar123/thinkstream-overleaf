\section{Streaming Protocol and Prompts}
\label{app:protocol_prompts}

\paragraph{Streaming protocol.}
WTI uses the same message contract for SFT, RL rollout, and evaluation.
Each current visual turn contains the timestamp \texttt{<t=N>}, the current 1-second video chunk, an optional \texttt{<active\_query>} block, and an optional \texttt{<response\_history>} block.
Historical state is carried as compact memory lines \texttt{<m t="start-end">summary</m>}.
If a trajectory resumes from compact memory, these \texttt{<m>} lines appear in a separate user turn, followed by the assistant acknowledgement \texttt{Memory loaded.}; the next user turn then starts with \texttt{<t=N>} and current frames.
This keeps prompt-side state aligned with the bounded KV-window rollout: current chunks are visual, while older evidence is either memory text or retrieved by recall.

\paragraph{Action and output grammar.}
The online action space contains silence, response, recall, and compact-memory update.
For ordinary streaming turns, the assistant must open with \texttt{<think>...</think>} and end with exactly one terminal action: \texttt{</Silence>} when no query is ready, \texttt{</Response> answer} when the active query is answerable, or a Qwen tool call to \texttt{recall}.
Recall is allowed only when the active query needs older visual evidence that is strictly earlier than the current chunk and is not already available from current frames, compact memory, response history, or a previous recall result.
For future-dependent questions, the prompt instructs the model to stay silent until the requested visual trigger or event completion is observed.
The parser marks malformed outputs, multiple terminal actions, future-looking recall intervals, and unsupported tool names as format/action errors.

\paragraph{Prompt templates.}
Streaming turns expose only the recall function.
Its arguments are absolute source-video seconds, \texttt{start\_time} and \texttt{end\_time}, defining a closed interval \([\texttt{start\_time},\texttt{end\_time}]\) that must be earlier than the current chunk.
At a compression boundary, the user payload contains \texttt{OLD\_MEMORY}, \texttt{NEW\_CAPTIONS}, the covered latest span, and instructions to preserve useful old memory while covering new captions with honest time ranges.
The compact-memory system prompt requires only XML memory lines of the form \texttt{<m t="start-end">one concise English summary</m>}.
It forbids JSON, Markdown, answers, analysis, and tool calls, and it instructs the model to merge adjacent complete units rather than repartition old ranges.

\section{Training, Rewards, and Implementation Details}
\label{app:implementation}

\paragraph{Masked SFT.}
Masked SFT uses the same bounded state as inference.
The vision encoder is frozen, while the language model and multimodal projector are updated.
Supervision is applied only to assistant-generated tokens; stream inputs, user queries, and environment observations are context only.
We average losses separately over action tokens and state-update tokens, then combine them with the bucket-weighted objective in Section~4, so frequent silence/state-update spans do not dominate action learning.

\paragraph{Stream-GDPO setup.}
Stream-GDPO starts from the SFT checkpoint and runs in the same chunk-level streaming environment used at inference.
Each rollout contains one video stream with one or more timed questions.
The policy is optimized on assistant action turns with group-normalized trajectory advantages.
The rollout environment supplies current chunks, recall returns, and compact-memory boundaries, so training and inference share the same online state transitions.

\paragraph{Reward design.}
Question-level rewards cover answer outcome, format validity, and recall use.
Recall rewards encourage requesting the support interval only when historical visual evidence is needed, while avoiding future-looking ranges.
The compact-memory reward is computed at the rollout level because memory quality is not tied to a single question.
Together, these rewards train correctness, timing, evidence use, and long-range history maintenance within one streaming policy.

\paragraph{Hyperparameters and compute.}
WTI is initialized from Qwen3-VL-8B-Instruct.
For SFT, we train chunk-level trajectories with learning rate \(1\times10^{-5}\).
For Stream-GDPO, we train for about 60 optimization steps with veRL on 8 H20 GPUs.
Table~\ref{tab:training_hyperparams} summarizes the main settings.
The reported Stream-GDPO run used roughly 55 minutes per step on 8 H20 GPUs, for approximately 440 H20 GPU-hours.
This accounting covers the main RL training run and excludes data generation, benchmark evaluation, and auxiliary diagnostics.

\paragraph{Evaluation protocols.}
We evaluate StreamingBench on the real-time visual understanding split and report task-level categories following the source benchmark.
For OVO-Bench, we report Real-Time, Backward, Forward, and weighted overall accuracy under the official trajectory weighting.
Video-MME, MLVU, and LongVideoBench use their source aggregate metrics.
All online evaluations are causal and do not expose future frames; offline/static baselines are restricted to the observed prefix in online benchmarks.
Entries marked ``--'' denote runs that are unavailable in the frozen result set or diagnostic values that are not reported.

\section{Responsible Use, Reproducibility, and Case Studies}
\label{app:responsible_use}

\paragraph{Artifacts and licenses.}
We use public pretrained models, benchmarks, and software packages for research training and evaluation, including Qwen3-VL-8B-Instruct~\citep{qwen3vl2025}, StreamingBench~\citep{streamingbench2024}, OVO-Bench~\citep{ovobench2025}, Video-MME~\citep{videomme2025}, MLVU~\citep{mlvu2024}, LongVideoBench~\citep{longvideobench2024}, and veRL/HybridFlow~\citep{sheng2024hybridflow}.
We cite their creators, follow corresponding access terms and licenses, and treat WTI-82K as a research artifact whose release is subject to source-artifact terms and institutional approval.

\paragraph{Intended use and privacy.}
The constructed data is derived from public video-derived sources and benchmark materials, then filtered for clear visual content, temporally locatable events, and QA/causal-grounding quality.
Because such data may contain identifiable people or sensitive scenes, downstream use should remain research-only and avoid surveillance, biometric identification, attempts to identify individuals, or safety-critical decision making.
The study does not involve recruited human subjects, paid annotators, or new human-subject data collection.

\paragraph{AI-assisted data construction.}
As described in Section~4 and Appendix~\ref{app:data_stats}, Qwen3.5-397B is used for candidate question generation, answer synthesis, and causal-consistency checks during WTI-82K construction; the authors verify the generated data, trajectories, claims, citations, and results.

\paragraph{Qualitative cases.}
Figure~\ref{fig:chronostream-motivation} illustrates the three behaviors checked by qualitative cases: active-window answering, historical recall after evidence leaves context, and silence until future evidence becomes available.
